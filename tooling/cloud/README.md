# @crossbind/cloud

crossbind cloud on `api.crossbind.dev`: the compile service behind the playground on crossbind.dev, the accounts that the playground page and `crossbind login` sign in to, and the snapshots `crossbind app preview --cloud` uploads, which `snapshots.crossbind.dev` serves to the account's own devices (below). A visitor's project, a `main.js` and C, C++ or Rust sources with packages from the playground's list, is built with crossbind into a wasm module, its loader and the list of what `main.js` imports from it; the page then runs them in the visitor's own browser.

## A compile

- Only the Worker in front reaches `compiler/server.js`: `POST /compile` with `{"files": {"main.js": "...", "native/greet.h": "..."}, "packages": ["port:sqlite3"]}`. Files are `main.js` and sources under `native/` named like C identifiers (`.h`, `.hpp`, `.cpp`, `.cc`, `.rs`), at most 16 of them and 64 KB in all; packages are ids from `compiler/packages.js`, at most 8. The compiler writes `crossbind.config.js` itself. One compile runs at a time, one more may wait, the rest get 503.
- Every compile starts from a copy of `compiler/template`, built once when the image is built at the same path, so cmake's and emscripten's caches are warm. The copy is removed afterwards. That build uses every package (`compiler/warm.js`) and leaves the store: the crates and Conan builds each compile works from without a network. `compiler/template/conan.lock` and `crossbind.cargo.lock` pin the Conan recipes and every crate, and an image build that resolves others stops with the diff to commit.
- `crossbind build -p wasm -a wasm32 -r st -e browser -b debug --bind-imports` runs in the sandbox below; the server returns the loader, the wasm (base64), the list of what `main.js` imports (`imports.json`) and the build log with workspace paths shortened.
- The site prebuilds every playground sample from the same template, crossbind and packages (`scripts/node-modules.mjs`, used by `scripts/site/build-example-demos.mjs`), so an unedited sample runs the module a compile would make, without one.

## Sandbox

The compiler is treated as compromised:

- **Namespaces** (bubblewrap): user, pid, network, ipc, uts and cgroup. No network, not even loopback to the server; no further user namespaces.
- **Syscalls** (seccomp, `compiler/seccomp.js`): io_uring, bpf, keyctl, perf events, userfaultfd, ptrace, process_vm and module loading fail; sockets open for the unix and internet families only, which keeps out vsock (the microVM's channel to its host), netlink and raw packets.
- **Files**: `/usr`, `/emsdk`, the Rust and Conan toolchains and the CLI read-only, emscripten's cache and the package store behind throwaway overlays, the workspace and a 256 MB `/tmp` writable, `/proc/cmdline` and other kernel files covered. The server code, the template, the store's own folder and `/etc/passwd` are not there.
- **Limits**: 60 s of CPU, 2 GiB of data (the CLI's own node maps about 1.8 GiB, mostly untouched), 128 MiB per file, 64 processes, 1024 open files, 45 s of wall clock and 8 MiB of output. A watchdog stops the compile when the machine (or its cgroup) gets under 256 MiB free, since a sandbox can reset its own OOM score and fill tmpfs mounts no size limit covers.
- **Environment**: the toolchain variables only.
- **Outputs** are read after the sandbox is gone, as regular files through real folders only: no links, FIFOs or oversized files (2 MiB of loader, 6 MiB of wasm, 1 MiB of import list, whose names must be identifiers).
- **Workspace**: removed with `chmod -R` and `rm -rf`, which walk trees deeper than a path can name. One that cannot be removed answers 500 and recycles the server.
- **Recycling**: after 200 compiles, failed ones included, the server takes no new work, answers what it holds and exits; the next compile starts a fresh container. tini is PID 1 and reaps what the sandboxes leave.

On Cloudflare every container is its own Firecracker microVM, started without internet access. The Worker gives a compile back only when the compiler turned it away before it started; a compile that ended the container, or whose answer came back unusable, stays counted.

## The Worker in front

`worker/` is the API on `api.crossbind.dev`. The playground page talks to it under `/playground`:

- `GET /session`: who is signed in, the day's limit and what is left of it, whether GitHub sign-in is set up, and the Turnstile site key.
- `POST /compile`: from the playground page's origin only, or with a token of the crossbind app (`Authorization: Bearer`), whose extension sends it by the host's own fetch: that compile is held to the token, not to the `Origin`, and counted for its account with no browser check. An anonymous visitor passes Turnstile first. A compile seen before comes from the cache without counting (a week for a module, ten minutes for a compile error); otherwise it counts against the visitor's network (an IPv6 /64 is one network) or their account, and against the day's total for everyone.
- `GET /callback/github` and `/callback/apple`: where GitHub and Apple send back a sign-in that the account's page started (below). GitHub sign-in asks for no scope; GitHub accounts younger than 30 days are turned away. PKCE (S256) binds GitHub's code to the browser that asked for it: the verifier waits in an HttpOnly cookie beside the state, so a code caught on its way is worth nothing elsewhere. The GitHub account signs in to its crossbind account (below), and the session is an HMAC-signed, host-only cookie holding the account's id and name.
- `POST /logout`. The site's playground signs in, and deletes its account, on the account's page below.

The account's own page is the Worker's, on this same origin (`worker/account-page.js`), so that no other site, crossbind.dev included, can change an account:

- `GET /login`: signed out, "Sign in with GitHub" and "Sign in with Apple", each once it is set up; signed in, the account's name, its sign-ins, each with Unlink unless it is the last, and Link for a provider set up that it lacks, its devices (its tokens, by label and first and last use) each with Sign out, "Sign out everywhere", Delete account behind a box to tick, and Sign out. Plain HTML with `/account.css` and `/account.js`, under `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; form-action 'self' <the playground's origin>; frame-ancestors 'none'; base-uri 'none'` (Chromium holds a form's POST whose redirect leaves `form-action`: linking goes on to `https://github.com` and `https://appleid.apple.com`, which the policy lists, and Make a new account to the playground), `Referrer-Policy: same-origin` (under `no-referrer` a form's POST carries `Origin: null`) and `Cache-Control: no-store`. `crossbind.dev/login/` leads here.
- `GET /account/login/github` and `/account/login/apple`: a sign-in's start, a link; signed in, it comes back to the page, to the device page with `?next=device`, or to `PLAYGROUND_URL` with `?next=playground`; anything else comes back to the page (`/login?next=device` or `/login?next=playground` for those), which says what happened. GitHub is sent the playground's callback, `/playground/callback/github`, the one the OAuth app lists, and Apple `/playground/callback/apple`, the return URL its Services ID lists. A notice with a date or another account's name in it reaches the page in a cookie of a minute, `__Host-pg_notice`, which it shows once: an address would let any link make one up.
- A first sign-in on the page with an identity crossbind does not know makes no account: the page asks, "No crossbind account signs in with this Apple ID yet", with Make a new account (`POST /account/new`). The identity its provider confirmed waits for the answer in a sealed, HttpOnly cookie of ten minutes, `__Host-pg_pending`, whose HMAC is taken under its name, so that neither a value written by hand nor another cookie's passes for it; an identity that has an account by then signs in to it. `crossbind login` on the CLI's route of before still makes an account at once, as that flow has no page to ask on.
- Linking starts as signing in does, with a navigation the Worker sends to the provider, from a form of the page (`POST /account/link/<provider>`): the state cookie names its purpose, `link:<account id>`, and the callback links only to that account, only while the browser's cookie still signs it in, so no script holds what the callback compares and a plain sign-in while signed in links nothing. An identity moves from no other account: one that another account holds, live, deleted with build seconds this month, or unlinked from it this month, is refused with the day it is free; one whose account is blocked, one of a provider the account already has, and a GitHub account younger than 30 days are refused too, each in words of their own. The question's other answer, signed in, links the identity it waits with (`POST /account/link-pending`). `POST /account/unlink` never takes the last way in (409); the identity is free at once when the account has no build seconds this month, and else held through the month, and unlinking GitHub blanks the account's GitHub name.
- Sign in with Apple asks Apple for no scope, so it hands over its id for the person, `sub`, and nothing else is read: no name, no email. The answer comes back in the query, bound to the browser by a nonce, the SHA-256 of a secret that waits in the HttpOnly state cookie, as GitHub's PKCE verifier does. The code is exchanged with a client secret the Worker makes for each sign-in, an ES256 JWT of five minutes signed with the key; the `id_token`'s issuer, audience, expiry and nonce are checked, and not its signature, as it comes from Apple's token endpoint over TLS. The refresh token Apple gives is revoked at once, so crossbind keeps no Apple token. An account with no GitHub account linked goes by "Apple account …1643", the last four digits of its id; its GitHub name is written by a GitHub sign-in alone.
- `POST /account/logout`, `/account/tokens/revoke` (`ref`: the first 16 hex digits of the token's hash, as the page lists it), `/account/logout-everywhere`, `/account/delete` (`confirm=yes`), `/account/new`, `/account/link/github`, `/account/link/apple`, `/account/link-pending` and `/account/unlink` (`provider`): the page's forms, which take a request whose `Origin` is this origin alone. Any other, crossbind.dev's too, and none or `null`, get 403; a form whose cookie no longer counts goes back to the page.
- Signing out everywhere, here or with `crossbind logout --all`, deletes every token of the account and sets `users.signed_out_at`, before which no cookie counts; each of the account's snapshots gets a new key, as when one crossbind app is signed out (Snapshots, below). Every route that reads the cookie reads the account's row: a cookie of an account deleted or blocked since, or made before it signed out everywhere, signs in nothing.
- `GET /device`: the device page, where a device's sign-in is approved (below). Signed out, "Sign in to approve a device" with a sign-in of each way in, which comes back to it (`?next=device`); signed in, "Enter the code your device shows", typed and never taken from the page's address. Its script posts the code to `POST /account/device/lookup` (`{"user_code"}`, in any case, with or without its dash), which answers what asked, from which country and when, and as which account it would sign in; then to `POST /account/device/approve` (`{"user_code", "approve": true}` or `false`), which answers the number, 10 to 99, to the page alone, or ends the code. Both take this origin alone and the cookie of a signed-in account (401 without one, 404 for no code waiting, 429 past ten codes entered a minute for an account or a network). Sign out there comes back to the page. `crossbind.dev/device/` leads here.

The CLI and the crossbind app talk to it under `/v1` (`worker/account-api.js`), with a token and without cookies or CORS:

- `POST /v1/device/authorize` and `POST /v1/device/token`: a device's sign-in, crossbind's own device flow (RFC 8628) with the number match (`worker/devices.js`), for the crossbind app and `crossbind login`. The device asks with no token, `{"client": "app", "version": "1.0.0", "platform": "ios", "os": "27.1"}` or `{"client": "cli", "version": "2.0.0-beta.79"}` and no other field, and gets a device code, a code of eight letters (`NPCC-CNQN`, of `BCDFGHJKLMNPQRSTVWXZ`), the device page `<this origin>/device`, ten minutes and a poll every five seconds. Its person enters the code on the device page and approves it there; the device polls with `{"device_code"}`, gets `matching_required` once the code is approved, and sends `{"device_code", "match"}` with the number the page showed: one try, compared and ended in one statement. It then gets a token (`{"access_token", "token_type": "Bearer", "account": {"id", "name"}}`) of the kind it asked as, which the account's page lists by what asked ("crossbind app 1.0.0 on iOS 27.1", "crossbind CLI 2.0.0-beta.79"). Refusals are RFC 8628's, the code in `error` and the words in `error_description`: `invalid_request`, `slow_down` (past ten starts a minute from a network, past 300 a minute for everyone together, or past 13 polls a minute for a code: the device adds five seconds), `authorization_pending`, `access_denied` (denied, the number wrong, the code used, or the account blocked), `expired_token`, `invalid_grant`. The device code is kept as its hash, with the letters, what asked, its country as Cloudflare reads it, and the number once approved; the daily prune deletes every code past its ten minutes.
- `POST /v1/login/device` and `POST /v1/login/token`: `crossbind login` of the releases before the device page, GitHub's device flow, kept for the CLIs installed. The user enters a code on github.com; the Worker, not the CLI, asks GitHub for the outcome, so no GitHub token leaves it. The CLI polls `/v1/login/token` (202 until the code is approved) and then receives a token of crossbind cloud's own (`cbt_…`). A GitHub account crossbind does not know gets its account at once.
- `GET /v1/usage`: the month's cloud build seconds by toolchain image against the monthly allowance (`BUILD_SECONDS_MONTHLY`), and the day's playground compiles. A new account's allowance is 0, with `opensOn`, the day its minutes open.
- `GET /v1/account`: the account the token signs in to, `{"id": "…", "name": "…"}`.
- `PUT /v1/sessions/<id>` and `DELETE /v1/sessions/<id>`: `crossbind app preview` lists the dev server it runs for the account's devices (`worker/project-sessions.js`). The id is 16 random bytes of the run's in base64url, and the body `{"source": "dev", "project": {"id", "name"}, "addresses": ["192.168.1.6:5173"], "protocol": 1, "key"}`: the project's id, 16 bytes in base64url, and its name, 1 to 64 letters, digits, spaces and `._@/-`; 1 to 4 addresses of the dev server, each a private IPv4 address, an IPv6 one in fc00::/7 or a name that ends in `.local`, as the CLI's own rule has it, with its port, and written as a URL writes it; the session protocol's number; and the pairing key, 32 bytes in base64url. It answers `{"id", "expiresAt"}`. The CLI sends the same body every five minutes while the preview runs, and a session leaves the list ten minutes after the last; `DELETE` as the preview stops. 409 for an id that another run or account holds, 429 past ten live dev sessions of an account, its snapshots apart. `DELETE` takes a dev session alone: a snapshot goes by its own life.
- `GET /v1/sessions` and `GET /v1/sessions/<id>`: the crossbind app's, which opens them: the account's live sessions, a snapshot once its first upload is in and none while snapshots are paused, the newest first, each with its pairing key, or one of them. A snapshot's has `"source": "snapshot"`, no address and its upload's `version`. 404 alike for another account's, an ended one and an unknown one.
- `POST /v1/snapshots` and `PUT /v1/snapshots/<id>`: `crossbind app preview --cloud` uploads the project's web build as a snapshot (`worker/snapshots.js`, below). The first takes `{"project": {"id", "name"}, "protocol"}`, as a dev session's are, and answers `{"id"}`: the cloud makes the snapshot's id and its pairing key at random, or finds the account's snapshot of that project again. 429 past three live snapshots of an account; one just made, or one that ended and is asked for again, waits an hour for its upload and counts meanwhile. The second takes the web build as one ustar archive with its `Content-Length` (411 without it, 413 at once past 50 MB and the archive's own room) and answers `{"id", "version", "files", "bytes", "expiresAt"}`; ten a minute for an account (429), and by the day, below.
- `DELETE /v1/token` and `DELETE /v1/tokens`: `crossbind logout`, for the token sent, or `--all`, which signs the account out everywhere as its page does. A crossbind app signs out with the first, which then gives each of the account's snapshots a new key, as the second always does.
- `DELETE /v1/account`: `crossbind account delete`, open to a blocked account too.

Every token has a kind (`tokens.kind`), the client its device sign-in asked as, and a label, what asked. The CLI's, `cli`, takes every route of `/v1` that takes a token but the two that read sessions, and the runners', and compiles nothing in the playground; the old routes issue it too. The crossbind app's, `app`, takes `GET /v1/account`, the two that read sessions, the three deletions and the playground's compile alone. A route refuses any other kind with 403.

Builds under `RUNNER=REMOTE` talk to it under `/runner/<image>/v1/*`, the runner protocol of `docs/api/remote-runner.md`, with the same token (`worker/runner-api.js`, below).

An account with no GitHub account linked is new for its first 30 days (`MIN_GITHUB_ACCOUNT_DAYS`, as a GitHub account must be that old to sign in): it compiles in the playground as itself, `NEW_ACCOUNT_DAILY` a day and without the browser check, and has no cloud build minutes, its runner routes answering 403 with the day they open. Linking a GitHub account ends it at once. Nothing new is stored for it: the account's `created_at` and its identities say it.

Every route counts requests per network (an IPv4 address or an IPv6 /64) with Workers rate limiting, before anything that costs: 120 a minute, 10 sign-ins started (a device's, and the CLI's of before), and 1,200 runner requests, since a build makes several per step. A device's polls count by its code's hash (13 a minute), and the codes entered on the device page by the account and by the network (10 a minute each). Workers counts each of these at each Cloudflare location, so the sign-ins that everyone starts together are counted exactly in the quota's Durable Object, 300 a minute (`STARTS_PER_MINUTE`), behind a limiter of one key at each location (300 a minute), which bounds what a flood from many networks sends it: such a flood holds sign-ins up while it lasts, and writes no row past the count. The snapshot host counts its requests on a limiter of its own, 3,000 a minute for a network, as a snapshot loads many files at once, and a snapshot's uploads count 10 a minute for an account, and by the day in the quota's Durable Object (Snapshots, below). Limits, allowed origins, the networks that may not compile without signing in (`BLOCKED_NETWORKS`, as `198.51.100.9,2001:db8:85a3:42::`), the kill switches (`PLAYGROUND_ENABLED`, `SNAPSHOTS_ENABLED`), the snapshot host (`SNAPSHOTS_HOST`), what every snapshot together may hold (`SNAPSHOTS_TOTAL_GB`) and the uploads a day of an account and of everyone (`SNAPSHOT_UPLOADS_DAILY`, `GLOBAL_SNAPSHOT_UPLOADS_DAILY`) are `vars` in `wrangler.jsonc`. Deleting the `GITHUB_CLIENT_ID` secret turns signing in with GitHub off, and deleting any of the four `APPLE_*` secrets signing in with Apple, whose button then leaves the page.

## Accounts

D1 (`migrations/`, binding `DB`) keeps every crossbind account, on the page or with the CLI, and the identities it signs in with: the GitHub user id or Apple's id for the person (`identities`), the GitHub name and when it signed in, never an email, a GitHub token or an Apple token; its tokens as SHA-256 hashes, with their kind and label, the 20 most recently used of the CLI's and the 10 of the crossbind app's per account, each dropped after 90 days unused; its cloud build seconds per month and image, for the current month and the three before it; and the sessions `crossbind app preview` registers, each with the project's id and name, the dev server's addresses and the pairing key: deleted as the preview stops, and else listed until ten minutes after its last renewal and kept until the next daily prune. An account made before identities keeps its GitHub id as its id; a new one gets an id of crossbind's own, drawn at random from 2^40 up to 2^53, above every GitHub id, by a plain `INSERT` that draws again when an account, or a deleted account's identities or seconds, name the id. A sign-in finds its account by its identity alone, never by a GitHub id. Blocking an account stops its sign-ins, compiles and tokens. Block by the account's id: a GitHub name passes to someone else after a rename.

Deleting an account removes it, its tokens, its sessions and its snapshots' files at once, and its earlier months of build seconds; the current month's stay under the bare id until the month ends, so a new sign-in does not bring a fresh month, and a blocked account stays as its id, or deleting it would lift the block. Its identities stay with those seconds, so that signing in with one brings the same id back with its month spent, and go with the last of them, or at once when there are none (the triggers of `migrations/0002`). An identity unlinked from an account that has build seconds this month is held through the month of its unlinking: it signs in to nothing until the 1st, when the daily prune deletes it, and the account's later builds do not hold it longer. Unlinked from an account without them, it is free at once. A cron trigger prunes daily what is kept only for a while (`prune` in `worker/accounts.js`), the devices' sign-in codes past their ten minutes (`worker/devices.js`), the sessions past their life (`worker/project-sessions.js`), and the snapshots' files no live snapshot names (`worker/snapshots.js`); `landing/src/pages/privacy.js` states the same periods, and a landing test holds the two together.

Query it from the repository root: in this package wrangler first validates `wrangler.jsonc`, which fails until a deploy or `pnpm build:image` has assembled the image contexts in `.build/`. The first finds an account by its GitHub name, the second blocks the account a GitHub account signs in to and ends its sessions and snapshots, whose files the daily prune then deletes, the third lists the accounts no linked identity signs in to, which only a rollback to the Worker before identities makes (each made then under its GitHub id), and the fourth counts the snapshots and what they hold, against `SNAPSHOTS_TOTAL_GB`.

```bash
tooling/cloud/node_modules/.bin/wrangler d1 execute crossbind-accounts --remote --command "SELECT id, login, last_login_at FROM users WHERE login = '<name>'"
tooling/cloud/node_modules/.bin/wrangler d1 execute crossbind-accounts --remote --command "UPDATE users SET blocked = 1 WHERE id = (SELECT user_id FROM identities WHERE provider = 'github' AND subject = '<GitHub id>'); DELETE FROM sessions WHERE user_id = (SELECT user_id FROM identities WHERE provider = 'github' AND subject = '<GitHub id>')"
tooling/cloud/node_modules/.bin/wrangler d1 execute crossbind-accounts --remote --command "SELECT id, login FROM users WHERE id NOT IN (SELECT user_id FROM identities WHERE unlinked_at IS NULL)"
tooling/cloud/node_modules/.bin/wrangler d1 execute crossbind-accounts --remote --command "SELECT count(1) AS snapshots, coalesce(sum(bytes), 0) AS bytes FROM sessions WHERE source = 'snapshot' AND upload IS NOT NULL"
```

GitHub sign-in needs a GitHub OAuth app with its callback at `https://api.crossbind.dev/playground/callback/github` and the device flow enabled; its client id and secret are the `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` secrets. The account's page signs in through the same callback.

Sign in with Apple needs, under the Apple developer team that publishes the apps (Apple's id for a person belongs to the team): a Services ID whose web domains are this host and staging's, with the return URLs `https://api.crossbind.dev/playground/callback/apple` and `https://api-staging.crossbind.dev/playground/callback/apple`, and a key with Sign in with Apple. All four values are secrets, so nothing of the Apple account is committed: `APPLE_SERVICES_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY`, the key's `.p8` whole (`wrangler secret put APPLE_PRIVATE_KEY [--env staging] < AuthKey_<key id>.p8`).

## Snapshots

`crossbind app preview --cloud` uploads the project's web build in preview mode, for the account's own devices: the crossbind app lists it and opens it from anywhere, through its proxy, as it opens a dev server on the network (`worker/snapshots.js`).

- **Kept** in R2 (binding `SNAPSHOTS`, the bucket `crossbind-snapshots`, staging's `crossbind-snapshots-staging`) as two objects an upload under `snapshots/<session>/<upload>/`: `archive.tar`, the archive as it was sent, and `index.json` beside it, each file's path with the offset and the size of its bytes in the archive; under a session of the source `snapshot`, whose row names its live upload. The first deploy makes the bucket under its `bucket_name`, as it makes the database.
- **Read as a stream, never whole:** the body passes through one `FixedLengthStream` of its declared length into the archive's one `put`, each header read as it passes, so an upload holds a few chunks of it in memory, not 50 MB, and takes the time its bytes take whatever its files: two writes, where a write a file took over a minute for 500 files. Each header's checksum holds; an entry is a regular file at a plain path (letters, digits and `_@.+-` between slashes, none of them `.` or `..`, nothing under `__crossbind/`, whose paths the host and the crossbind app answer themselves), an `index.html` among them, and the archive ends with its empty block. 500 files and 50 MB at most, each checked before a file's bytes pass, and 503 past what every snapshot together may hold (`SNAPSHOTS_TOTAL_GB`, 20 in production); what follows the archive's end passes unread, within the room its length's check leaves. A refusal aborts the put, so that R2 keeps nothing of it and nothing is cleaned up, and a failure that is no refusal (R2 failing a put, a connection cut) answers 503 in crossbind's words, which Cloudflare passes on as they are, its own going to the log alone. Then the index, and the upload live, when its `version` rises and the upload before it is deleted; should the index or that `UPDATE` fail, the upload's two objects are deleted, kept going by `waitUntil` for a client that left.
- **Lives** 30 days after its last upload; three an account.
- **Counted** by the day, exactly, in the quota's Durable Object as compiles are, under keys of their own: 50 uploads a day for an account (`SNAPSHOT_UPLOADS_DAILY`, 429 past it) and 1,000 for everyone (`GLOBAL_SNAPSHOT_UPLOADS_DAILY`, 503), as R2 bills each object an upload writes, two, and the minute's limiter is counted at each Cloudflare location: 2,000 writes a day at most. An upload counts once the checks that read nothing have passed (the switch, the id, the minute's limit, the length, the snapshot, the total) and before a byte of its archive is read; a refusal after that stays counted.
- **Served** from `https://snapshots.crossbind.dev/<session>/<path>` (staging's `snapshots-staging.crossbind.dev`; `SNAPSHOTS_HOST`), a custom domain of this Worker that answers GET and HEAD of a live snapshot's files, of an account not blocked, and nothing of the API's: no route under `/v1` or `/playground`, no page, no cookie. Every request needs `x-crossbind-preview`, the HMAC-SHA256 of the session's pairing key over `crossbind-requests`, as `crossbind app preview`'s dev server takes it from the crossbind app's proxy; without it, 403, the same for a snapshot that is not there, and for `/__crossbind/session?challenge=<32 bytes>` too, which answers as the dev server does: the protocol, the session (the project's name, the account's id and name, the snapshot's id and version) and the key's proof over them and the challenge. A file is found in its upload's index by the index's own entries alone, which an isolate reads from R2 once while it keeps it (64 uploads' at most, the least lately used going first, and no answer rests on what is kept), and is answered as a ranged read of the archive, an empty one with no read; an upload with no index, of the layout before, answers 404 for each file until the next upload replaces it. A file comes with `Content-Security-Policy: sandbox; default-src 'none'`, `nosniff` and `no-store`. The API's own host answers no snapshot.
- **Keyed** anew whenever a device that may have read the keys is signed out: a crossbind app, by `DELETE /v1/token` with its token or by Sign out of that device on the account's page, and every device at Sign out everywhere (`DELETE /v1/tokens`, or the page's). Each of the account's snapshots then gets a new key drawn at random, so the host answers the old key's token 403, and a device still signed in reads the session again (`GET /v1/sessions`) and opens it with the new one. A CLI's sign-out changes nothing: no CLI is sent a key.
- **Paused** with `SNAPSHOTS_ENABLED`: uploads and the host answer 503, and the list leaves snapshots out.
- **Deleted** with the account, files and all, at once; the block query above deletes a blocked account's sessions, and the daily prune deletes every file no live snapshot names once it is an hour old: a replaced upload's, a refused one's that its cleanup missed, an ended or blocked snapshot's. The bucket's lifecycle rule, objects older than 31 days, is a backstop of the maintainer's: `tooling/cloud/node_modules/.bin/wrangler r2 bucket lifecycle add crossbind-snapshots snapshots-31-days snapshots/ --expire-days 31` (staging's bucket likewise).

## Cloud runners

`worker/runner.js` gives every account a runner of each toolchain image: a Durable Object named after the account's id, holding one container. Each container is a Firecracker microVM of its own, so builds of different accounts share nothing.

- **Image**: the toolchain image this repository's crossbind pins, with `core/crossbind/src/runner` copied in (`runner/Dockerfile`, assembled into `.build/runner-<image>/` by `scripts/build-image.mjs`). Older crossbind releases pin other images, and the runner turns their builds away with `toolchain mismatch`.
- **Requests**: the Worker checks the token, then passes the request on with the account's id in `x-crossbind-user` and, of the caller's headers, only the ones the runner protocol reads (`content-type`, and `content-range` and `x-crossbind-upload` for a file sent in parts): no token, no cookies. A token found valid in the last 30 seconds skips the D1 read and counts on the runners' rate; any other counts on the general one first, so made-up tokens cannot spend D1 reads. The runner's own token is derived from `RUNNER_SECRET` (32 characters at least, or every runner route answers 503), the image and the account, so nothing is stored. The entrypoint starts the runner as the image's unprivileged user, with no capabilities and `no_new_privs`. Build steps run as that user and can read the runner's token from its process; it opens nothing, since only the Durable Object reaches the container.
- **Network**: crates.io, ConanCenter and GitHub (`ALLOWED_HOSTS`), and only to download: GET, HEAD and git's fetch go out, pushes, form posts and uploads are refused (403). Other hosts get Cloudflare's 520, every name resolves to its egress proxy, and no other TCP or UDP leaves. Cloudflare intercepts the HTTPS to hold it to them; the entrypoint adds its CA to the system store at start, and Python reads that store through `REQUESTS_CA_BUNDLE`.
- **Time**: a runner is up from a build's first request until a minute after its last (`RUNNER_IDLE_SECONDS`), and that time is what counts: `worker/metering.js` adds it to D1 every minute. Counting steps alone would let a one-second step every few minutes keep a runner up for free.
- **Stops**: a runner does not start, and a step does not run, once the account's month (`BUILD_SECONDS_MONTHLY`), everyone's month (`GLOBAL_BUILD_HOURS_MONTHLY`) or everyone's day (`GLOBAL_BUILD_HOURS_DAILY`, so a burst of accounts cannot spend the month at once) is spent. Every minute the runner is checked again, and destroyed once one of them is spent, builds are paused (`CLOUD_BUILDS_ENABLED`), its account is blocked, it could not be metered three minutes running, or it has run longer than a whole month's allowance, which needs no D1 to tell. Every stop is a destroy: the runner is PID 1, which ignores a SIGTERM it has no handler for, and its build steps could stop it from handling one.
- **Cost ceiling**: `max_instances` runners per image at once (2), `standard-4` each.

## Commands

- `pnpm test`: unit tests.
- `pnpm build:image [--amd64]`: builds the compiler image from this repository's crossbind with the dependencies the lockfile pins (`pnpm deploy`), on the web toolchain image that crossbind pins, and writes the runner contexts beside it (`docker build .build/runner-web` builds one). The ports of `compiler/packages.js` come from npm, refused unless their integrity is the one pinned there; the template's build in the image fetches the crates and Conan packages.
- `pnpm attack`: runs the image with Docker and checks hostile compiles (file reads through `#include`, `#embed`, `.incbin`, SWIG and Rust's `include_bytes!`, compile-time bombs) and the sandbox from inside. bubblewrap needs Docker's seccomp filter and `/proc` masking lifted; a Cloudflare microVM allows it as it is.
- `pnpm run local`: the API on `localhost:8686` for the landing's dev server (`VITE_PLAYGROUND_API=http://localhost:8686/playground pnpm --filter @crossbind/landing dev`): the Worker's request handling in front of the image in Docker, quota, cache and accounts in memory. `wrangler dev` cannot run the compiler, since bubblewrap needs Docker's seccomp filter and `/proc` masking lifted. With `--github-client-id <id>` of an OAuth app whose device flow is enabled, the CLI's route of before signs in for real (a crossbind of the releases before the device page: `CROSSBIND_CLOUD_URL=http://localhost:8686 crossbind login`); today's `crossbind login` approves its code on the device page, whose sign-in on the web this API does not set up, so `check:local` runs it, against stand-ins.
- `pnpm run dev`: `wrangler dev` with the staging settings, for the Worker alone, on a local D1 the migrations are applied to first.
- `pnpm run check:local`: the account's pages against `wrangler dev` of `test/local/wrangler.jsonc`, with no container, on a local D1 made for the run and stand-ins for GitHub and Apple, whose key is made for each run: Chromium, from the workspace's Playwright, signs in, signs devices out, signs out everywhere and deletes the account, while a page of the site's origin is refused; a device signs in on `/device`, `scripts/device-check.mjs` playing the crossbind app and `crossbind login`'s own code the CLI, each typing the number read off the page, a code is denied, the site's approval is refused, and the page's own sign-in comes back to it; then a first sign-in's question and Sign in with Apple; `crossbind app preview`, with a Vite that stands in for one, signed in on the device page, lists its session, which `scripts/session-check.mjs`, playing the crossbind app of the GitHub account's and the Apple ID's accounts, finds for the first alone, and which a Ctrl-C takes off the list; `crossbind app preview --cloud` uploads the web build such a Vite writes into a local bucket, which `scripts/snapshot-check.mjs` opens through the snapshot host, `127.0.0.1`, finding the caps held, and which the account's deletion empties; then linking and unlinking both ways, and an identity held with its day. Chromium resolves no name but `localhost`, and wrangler asks Cloudflare for no request details (`CLOUDFLARE_CF_FETCH_ENABLED=false`, so every request comes from Miniflare's made-up US), so nothing leaves the machine.
- `node scripts/device-check.mjs [--url <cloud>]`: the device sign-in, checked against a crossbind cloud that is up, staging by default. It starts a sign-in as the crossbind app does, prints the code to enter on the cloud's device page, asks for the number that page shows once the code is approved there, and prints the account its token signs in to; then it shows that the token is the app's (its account read, usage refused) and signs it out.
- `node scripts/session-check.mjs --session <link> [--url <cloud>]`: a session of one account invisible to another, checked against a crossbind cloud that is up, staging by default, with the link `crossbind app preview` prints there. It signs in as the crossbind app twice, each time with a code approved on the device page: as the account that runs the preview, which lists the session with its pairing key and finds it by its id, then as another account, unlinked from the first, which lists nothing of it and gets 404 for its id; once the preview is stopped, the first finds it gone. Both tokens are signed out, and no token, key or address is printed.
- `node scripts/snapshot-check.mjs [--session <link>] [--url <cloud>] [--snapshots <host>]`: snapshots, checked against a crossbind cloud that is up, staging and its snapshot host by default. A test client signs in as `crossbind login` does and as the crossbind app does, each with a code approved on the device page by the account to check; a snapshot of 50 MB of files and one of 500 small files go up, one past either cap gets 413, and the one before it stays, listed at its version and served. Its uploads are of a made-up project, the same at each run, which the account keeps as one of its three snapshots for 30 days. With the link `crossbind app preview --cloud` printed for that account, it first opens that snapshot through the snapshot host with its key's token, and finds it refused without one. About 100 MB go up; each upload prints its seconds, and each refusal its words, crossbind's or the title of the page that came back instead. Both tokens are signed out, and no token, key or id is printed.
- `pnpm run deploy:staging`, `pnpm run deploy`: assemble the image contexts, deploy (wrangler builds the compiler and the four runner images for linux/amd64 with the local Docker and pushes them), and apply the D1 migrations the database lacks. The first deploy creates the database under its `database_name`, by which later deploys find it, the snapshots' bucket under its `bucket_name`, and the custom domains of the API and of the snapshot host. A migration only ever adds, since the code it ships with runs a moment before it does. `deploy` refuses uncommitted changes to crossbind, this package or the lockfile, which staging takes as they are, to try them before a commit; both refuse an overridden toolchain image.
- Staging answers on `api-staging.crossbind.dev`. The landing's dev server reaches it with `VITE_PLAYGROUND_API=https://api-staging.crossbind.dev/playground`, and `CROSSBIND_CLOUD_URL=https://api-staging.crossbind.dev` points the CLI at it. The page on `localhost` stays signed out, since the session cookie is not sent to another site; `/playground/session` opened directly shows a web sign-in.
